# ARCHITECTURE.md — як влаштований віджет

Однопотоковий **event loop tao** плюс маленький **tokio runtime**
(2 воркери) для мережевих запитів. UI рендериться на CPU
(tiny-skia → softbuffer), тож GPU не потрібен узагалі.

```
main.rs ── захист від другого екземпляра, логування, app::run()
   │
app.rs ─── володіє всім: конфіг, дані, вікно, меню, вікно вибору
   ├── monitor/scheduler.rs   tokio-задача: цикл fetch_all → sleep(interval);
   │                          CycleHook виконується після запитів кожного циклу
   │     └── providers/       claude.rs / codex.rs / copilot.rs / antigravity.rs /
   │                          grok.rs / cursor.rs (+ cursor/session.rs: власний
   │                          вхід і сеанс віджета в Cursor)
   ├── rows.rs                які рядки показують віджет і підказка:
   │                          SUB_ROWS (додаткові рядки), підпис моделі
   │                          частинами, межа ширини назв моделей (NAME_SLOTS)
   ├── choices.rs             що показує вікно вибору і що кожна його дія
   │                          робить із конфігом (чисто: без вікна, без файлів)
   ├── consent.rs             файли й сервери, які називає кожне запитання
   │                          (READ_INFO); found_tools лише перевіряє, чи є папки
   ├── models/                підписи моделі: settings.rs (файл налаштувань
   │                          кожного інструмента), session.rs (кінець
   │                          найновішої сесії), files.rs (обмежене читання,
   │                          відбитки змін), name.rs (загальне правило назв,
   │                          без таблиці)
   ├── ui/picker.rs           вікно «Rows and models»: Picker (чистий автомат
   │                          станів) + PickerWindow (тонке вікно tao)
   ├── ui/renderer.rs         малювання tiny-skia (ЄДИНЕ місце, що малює)
   ├── ui/layout.rs           прямокутники зон за лейаутом/деталізацією і Shape
   │                          (рядки + рядки моделі), за яким іде перекомпонування
   ├── ui/theme.rs            всі кольори (ЄДИНЕ джерело кольорів)
   ├── ui/context_menu.rs     нативне меню muda
   ├── ui/tray.rs             трей-іконка, спільне малювання гліфів і tooltip
   ├── ui/taskbar_panel.rs    індикатор-overlay на таскбарі (layered-вікно)
   ├── monitor/trend.rs       burn-rate проєкція (опційний прогноз)
   ├── platform/win.rs        Win32: WinEvent-стеження за таскбаром/треєм,
   │                          layered-презентація, промоція трей-іконок
   ├── updater.rs             щоденне опитування GitHub Releases, перевірка
   │                          SHA-256, тихе встановлення + перезапуск
   ├── platform/taskbar_geom.rs  чисті правила розміщення/фолбеку панелі
   │                          (тестуються без Win32)
   ├── platform/sqlite.rs     read-only запити до чужої SQLite-бази
   │                          (state.vscdb Cursor) через winsqlite3
   ├── config/ (schema.rs, storage.rs)  структури конфігу + толерантний TOML,
   │                          міграція [reads]
   └── notifications/toast.rs Windows-тости
```

## Потік даних

```
[Scheduler] --sleep(SharedInterval)--> [Provider::fetch()]
        кожен провайдер у власній tokio-задачі
                  │ ProviderData
        tokio mpsc → EventLoopProxy(UserEvent::Command)
                  │
   [event loop: обробник UpdateProvider]
   ├─ перевірка порогу для toast (з cooldown)
   ├─ merge/збереження provider-cache (непротухлі метрики переживають рестарт)
   ├─ retention застарілих даних (помилки не затирають реальні дані)
   └─ visible_data() → rows::visible_rows() → layout::Shape;
      перекомпонування лише коли Shape змінився → redraw
```

Кліки меню йдуть тим самим шляхом: `muda::MenuEvent` → proxy →
`UserEvent::Menu` → обробники змінюють конфіг, перебудовують провайдерів
(`SharedProviders` — це `Arc<RwLock<Vec<Arc<dyn Provider>>>>`, спільний зі
scheduler'ом), зберігають конфіг і просять redraw.

Підписи моделі читаються на тому самому циклі:

```
[Scheduler] fetch_all → CycleHook → spawn_model_read
        ModelJob { reader, request: (generation, ModelRequest) }
                  │ spawn_blocking: ModelReader::read — лише те, що дозволяє
                  │ [reads], файл повторно — лише якщо змінились mtime чи довжина
        tokio mpsc → AppCommand::Models(generation, Models)
                  │
   [event loop] старше покоління → відкидається; інакше layout::Shape → redraw
```

`model_request` дорівнює `None`, поки не позначено жодної частини підпису
або не дозволено жодного читання моделі, і тоді хук нічого не робить. Кожна
зміна запиту (`refresh_models`) збільшує покоління, тож читання, що почалося
до неї, ніколи не показується. Запит і читач мають окремі замки: event loop
бере лише запит і лише на мить, а повільний диск тримає тільки блокувальний
потік.

Вікно вибору — друге вікно, яке існує лише поки відкрите. Його події
відбираються за `WindowId` раніше за гілки віджета й ідуть у
`PickerWindow::handle_window_event`, яке передає їх чистому `Picker` і
повертає `PickerAction`. `choices::apply` перетворює кожну дію на зміну
конфігу плюс `Applied` (перебудувати й опитати провайдера, перечитати
моделі, зберегти й перекомпонувати, закрити); далі app.rs одразу оновлює
віджет, панель, трей і меню та дає вікну вибору свіжий `PickerInput`. Вікно
вибору ніколи не торкається файлів. Воно відкривається з меню
(*Rows and models...*), кліком по написові віджета «Choose what to show»,
саме на старті, поки `[reads] pending` каже, що ще треба показати вітання чи
повідомлення після оновлення, і з меню Providers, коли позначено провайдера,
якому ще нічого не дозволено (одразу на запитанні про нього).

## Ключові рішення

- **softbuffer + tiny-skia, не DirectX/OpenGL** — для барів і тексту GPU
  є чистим overhead'ом; копія framebuffer'а тривіально дешева, CPU у
  спокої 0%.
- **Blur через `SetWindowCompositionAttribute` ACCENT_ENABLE_BLURBEHIND (3)** —
  у acrylic (4) відомий баг DWM (кидає блюр при перетягуванні/зміні
  монітора). Accent перезастосовується циклом off→on після drag, при
  фокусі та при зміні DPI — це змушує DWM перезапустити завислий блюр.
- **Drag стартує з першого CursorMoved**, а не з кліку: кешована позиція
  курсора може бути застарілою одразу після контекстного меню, через що
  вікно колись телепортувалось.
- **2 tokio-воркери** — дефолтний воркер-на-ядро (тут 32) марнував ~30
  потоків на три крихітні HTTP-запити за цикл.
- **Один екземпляр** через named mutex у `main.rs`.
- **SQLite через власний `winsqlite3.dll` Windows, а не вбудований рушій** —
  Cursor тримає сеанс у SQLite-базі, і один індексований SELECT на хвилину не
  виправдовує вкомпільованого SQLite: `rusqlite` з `bundled` додає до exe
  `release-min` близько 1 МБ (+29%), FFI-читач разом із усім провайдером —
  13 КБ (виміряно 2026-11-10). DLL постачається з Windows 10 і 11 і
  вантажиться лише з System32 (`LOAD_LIBRARY_SEARCH_SYSTEM32`) при першому
  запиті, після чого лишається. Це не імпорт, тож машина без неї отримує
  чесну помилку, а не exe, що не стартує. З'єднання — `SQLITE_OPEN_READONLY`
  з busy timeout 200 мс. Виміряно: ~0.6 мс на запит; +0.2 МБ приватної
  пам'яті після першого, з виходом на плато нижче +0.5 МБ за 21 000 запитів.
- **Чесні стани відображення** (див. PROVIDERS.md): retention → сірий +
  давність → оцінки `≈0%` після гарантованого скидання. Один предикат,
  `ProviderData::is_aged` (застаріле чи оцінка), керує і сірими рядками
  віджета, і блідішим чорнилом панелі на таскбарі; кеш перемальовування
  панелі тримає його для кожного намальованого рядка, тож рядок
  перемальовується, коли стає застарілим чи знову свіжим, і більше жодного
  зайвого разу.
- **Монотонний якір застарілості**: чи live-дані «застарілі» — вирішується за
  монотонним годинником (`ProviderData.received_at: Instant`), а не настінним,
  тож стрибок часу (NTP/VM/DST) не може хибно посіріти свіжі дані чи вигадати
  скидання. Настінний час лишається для показу давності й відліків; оцінка
  `≈0%` ще й вимагає, щоб скидання минуло понад невелике вікно grace.
- **Пауза простою не старить дані**: планувальник повідомляє, коли ставить
  опитування на паузу через неактивного чи заблокованого користувача і коли
  відновлює його (`providers::set_polling_paused` → `PollingPause`). Live-дані
  ніколи не застарілі під час паузи, а після неї остання пауза віднімається
  з їхнього монотонного віку. Пам'ятається лише вона одна: між двома паузами
  завжди проходить цикл опитування, тож live-дані, старші за попередню паузу,
  належать провайдерові, що впав, і раніше посіріти для них чесно. Записи
  дискового кешу (без монотонного якоря) лишаються на правилі настінного
  часу.
- **Згода — одна таблиця конфігу, яку читають у двох місцях.**
  `Config::provider_active` (увімкнений І дозволений через `[reads] sign_in`
  чи `app_sign_in`) вирішує, чи провайдер узагалі працює й показується;
  провайдер, якому нічого не дозволено, будується вимкненим і повертає
  `NotConfigured`, перш ніж торкнутися файлу, keyring, `gh` чи мережі.
  `build_providers` ще й ставить `ProviderConfig::tool_files` лише за
  `sign_in` (ніколи не зберігається), і кожен провайдер перевіряє його перед
  будь-яким джерелом, що належить іншому інструментові: його файлом токена,
  його записом у Credential Manager, `gh auth token`, `state.vscdb` Cursor.
  Провайдер, налаштований лише власним входом програми (вставлений ключ
  чи токен використання, вхід у Cursor з меню), користується тільки ним і ніколи не переходить на
  файли інструмента. Якщо у вікні вибору зняти всі рядки провайдера,
  викликається `Config::revoke`. Текст кожного запитання береться з
  `consent::READ_INFO`, а тест звіряє його сервери з URL у коді провайдерів.
- **Звідки взявся конфіг, вирішує, що дозволено** (`storage::Origin`; стан
  встановлює `settle_reads` після проходів `migrate`, що перейменовують і
  дописують відсутніх провайдерів). `FreshInstall` (файлу немає, його не
  вдалося прочитати й він відкладений як `config.toml.corrupt`, він
  порожній чи без провайдерів) очищує `[reads]`, вимикає всіх провайдерів,
  тож і старіша версія після відкату нічого не читає, і позначає, що треба
  показати вітання. `Upgrade` (`[[providers]]` без `[reads]`: 0.7.0 і
  старіші) дозволяє кожного провайдера, увімкненого у файлі, і позначає, що
  треба показати одноразове повідомлення. Прохід дописування за будь-якого
  походження додає відсутнього провайдера вимкненим: версія, що записала
  файл, його не знала, тож і не читала.
  `Current` лишається таким, яким його лишив користувач.
- **Вигляд за замовчуванням зафіксовано.** Поки `[ui.rows]` і `[ui.model]` не
  задані, `rows::visible_rows` дає по одному рядку на провайдера з його
  даними без змін, а підказка панелі — колишній один рядок. Модуль лише для
  тестів (`ui/visual_baseline.rs`) звіряє віджет, панель, трей-іконку й
  підказку при наведенні, намальовані з конфігом за замовчуванням, із
  хешами pixmap, записаними з 0.7.0, і падає на будь-якому зміненому пікселі.
- **Назви моделей обмежено справжньою шириною, а не кількістю символів.**
  `rows::NAME_SLOTS` перелічує найвужчі місця, де renderer малює назву
  моделі (ширина й розмір шрифту); `name_fits` міряє через
  `Renderer::text_width`, тією самою мірою, що й `draw_text`, тож
  перейменована модель видна повністю в кожному розмірі. Тест renderer'а
  звіряє цей перелік із геометрією.
- **Вікно вибору — чистий автомат станів за тонким вікном.** `Picker` бере
  `PickerEvent` і повертає `PickerAction` плюс `PickerScene` із фігур, і все
  це тестується без вікна; `PickerWindow` показує його через softbuffer, як
  віджет, перемальовує лише на ввід і не має таймерів. Буфер обміну він
  читає лише на Ctrl+V у поле назви, яке редагується.

## Споживання ресурсів (виміряно, не оцінено)

Аудит 2026-08-23 скриптом `bench/perf_audit.ps1` (5 хв на 1 Гц, запущений
`release-min`, Win11 26200, Ryzen 9 9950X3D / 32 потоки, elevated). CPU —
точний облік ядра ОС, не семплінг. Звіт:
`bench/results/perf-audit-published-2026-08-23.json`. Прогін 2026-07-08 лежить
поруч як `perf-audit-published-2026-07-08.json` і показував 0.024% ядра та
61 МБ — те саме вікно на тій самій машині, на п'ять релізів раніше.

Перевиміряно 2026-09-23 для 0.7.0, 255 с на тихій машині (грало відео і
більше нічого; без підвищених прав, тому рядки про роздільність таймера й
SRUM перенесені з серпневого прогону). Панель уже питала шелл про місце в
барі — це той стан, у якому вона перебуває завжди, коли видима.
