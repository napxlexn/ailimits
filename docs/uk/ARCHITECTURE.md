# ARCHITECTURE.md — як влаштований віджет

Однопотоковий **event loop tao** плюс маленький **tokio runtime**
(2 воркери) для мережевих запитів. UI рендериться на CPU
(tiny-skia → softbuffer), тож GPU не потрібен узагалі.

```

   │       вже працює), логування, crash log, app::run()
app.rs ─── App: володіє всім (конфіг, дані, вікно, меню, вікно вибору);
   │       run() будує його, а event loop — це один виклик App::handle()

   │                          перевіряється) чи видалений ключ або usage-токен,

   │                          вхід і сеанс віджета в Cursor);
   │                          proxy.rs (проксі Windows), mod.rs (спільні
   │                          помічники запитів, слова помилок, перевірка
   │                          вставлених токенів)
   ├── rows.rs                які рядки показують віджет і підказка:
```

`bin/ailimits-auth.rs` — консольний інструмент `ailimits-auth.exe` (status;
збереження й видалення ключів і usage-токенів; вхід і вихід Cursor). Він
користується провайдерами й конфігом бібліотеки, але не циклом подій
віджета, і ніколи не викликає `follow_windows_proxy`, тож іде лише за
змінними проксі (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`).
`tools/release-signer` (окремий крейт з єдиною залежністю ring) створює
ключ релізу, робить і перевіряє підписи релізів; він підключає файл
застосунку `updater/signature.rs` (ключі, підписуване повідомлення, формат
файлу) як є, тож вони ніколи не розходяться, і в застосунок ніколи не
збирається.

## Потік даних

```
[Scheduler] --sleep(SharedInterval)--> [Provider::fetch()]
        кожен провайдер у власній tokio-задачі
                  │ ProviderData
        tokio mpsc → AppCommand::UpdateProvider { data, serial }
                  │
   [event loop: обробник UpdateProvider]
   ├─ serial уже не провайдерів? → відкидається (не показ, не кеш, не сповіщення)
   ├─ сповіщення про поріг + хук on_threshold (раз на вікно ліміту, alerts.json)
   ├─ хук on_reset (падіння на понад 30 пунктів від рівня не нижче порогу)
   ├─ тренд burn-rate і прогноз (показується, поки ввімкнено Forecast)
   ├─ хук on_startup (раз за запуск, на першу відповідь Ok)
   ├─ merge provider-cache (непротухлі метрики переживають рестарт)
   ├─ retention застарілих даних (помилки не затирають реальні дані)
   └─ active_data() → rows::visible_rows() → layout::Shape;
      перекомпонування лише коли Shape змінився → redraw
```

`SharedProviders` — це `Arc<RwLock<Vec<ProviderSlot>>>`, спільний зі
scheduler'ом, де `ProviderSlot { serial, provider }`. Кліки меню йдуть тим
самим шляхом: `muda::MenuEvent` → proxy → `UserEvent::Menu` → обробники
змінюють конфіг, зберігають його і просять redraw. Дії вікна вибору (нижче)
перебудовують провайдерів, чий `BuildKey` змінився (або, коли змінився
обліковий запис: вхід чи вихід у Cursor, вставлений чи видалений ключ або
usage-токен, інше джерело, вибране в Sign-in, провайдер, увімкнений чи
вимкнений своїми рядками, дана чи відкликана згода, — того одного
провайдера, з новим serial) і одразу опитують кожного перебудованого. Коли
змінилося його джерело чи обліковий запис, у перебудованого провайдера
очищаються кешовані числа, остання помилка, тренд і позначки сповіщень, і
його рядок показує Loading до першої відповіді; перебудова лише через Grok
Bot їх зберігає. Інші провайдери зберігають свої екземпляри, а з ними й те,
що тримають між циклами: відповідь gh, план Cursor і лічильник відмов,
проєкт Antigravity; перебудований екземпляр починає це спочатку.

`surface_rows` бере активні дані такими, як вони прийшли; `rows::visible_rows`
старить кожен рядок окремо (власний рядок провайдера — за його власними
вікнами, додатковий рядок — за його власною метрикою), тож скидання метрики
лише для додаткового рядка (скажімо, тижня Fable у Claude) ніколи не робить
сірим власний рядок провайдера. Трей і панель беруть `visible_data` =
активні дані, зістарені для показу, а щойно стовпець Taskbar у вікні
вибору змінювали (задано `ui.rows.taskbar`), — лише позначених там
провайдерів (`rows::taskbar_ticked`, щонайбільше два).

Підписи моделі читаються на тому самому циклі:

```
[Scheduler] fetch_all → CycleHook → spawn_model_read
        ModelJob { reader, request: (generation, ModelRequest) }, ReadGate
                  │ spawn_blocking: ModelReader::read — лише те, що дозволяє
                  │ [reads], файл повторно — лише якщо змінились mtime чи довжина
                  │ (або минуле читання не вдалося)
        tokio mpsc → AppCommand::Models(generation, Models)
                  │
   [event loop] старше покоління → відкидається; інакше layout::Shape → redraw
```

`model_request` дорівнює `None`, поки не позначено жодної частини підпису
або не дозволено жодного читання моделі, і тоді хук нічого не робить; інакше
він називає кожного провайдера, що працює (`Config::provider_active`). Кожна
зміна запиту (`refresh_models`) збільшує покоління, тож читання, що почалося
до неї, ніколи не показується, а відкликане читання нічого не читає.
`ReadGate` дозволяє одного читача водночас: запит, що надійшов під час
читання, лише позначає, що треба ще одне, і робітник, що вже працює, читає
знову із запитом, яким той є на ту мить, тож повільний диск ніколи не
накопичує блокувальних потоків. Запит і читач мають окремі замки: event loop
бере лише запит і лише на мить.

Вікно вибору — друге вікно, яке існує лише поки відкрите. Його події
відбираються за `WindowId` раніше за гілки віджета й ідуть у
`PickerWindow::handle_window_event`, яке передає їх чистому `Picker` і
повертає `PickerAction`. `choices::apply` перетворює кожну дію на зміну
конфігу плюс `Applied` (перебудувати й опитати провайдера, перечитати
моделі, зберегти й перекомпонувати, закрити); далі застосунок одразу
оновлює віджет, панель, трей і меню та дає вікну вибору свіжий
`PickerInput`. Дії блоку Sign-in (вибір джерела, вставлення, видалення,
вхід у Cursor, скасування, вихід) натомість ідуть у `app/sign_in.rs`, який
звертається до буфера обміну, Credential Manager і браузера та кладе свій
результат у `PickerInput` (`choices::SignInState`). Вікно вибору ніколи не
торкається файлів. Воно відкривається з меню (*Rows and models...*),
кліком по написові віджета «Choose what to show» чи «Nothing to show yet»
і саме на старті, поки `[reads] pending` каже, що ще треба показати
вітання чи повідомлення після оновлення. Коли воно відкривається саме, то тихо
(`PickerWindow::open_quietly`, без активації), і чекає, поки вікно на весь
монітор на передньому плані (`platform::foreground_fills_its_monitor`);
відкривається при наступній зміні вікна на передньому плані, наступному
оновленні провайдера чи наступному запуску програми (другий запуск будить
той, що працює, повідомленням його прихованому вікну підказки,
`UserEvent::ShowWidget`).

## Ключові рішення

- **softbuffer + tiny-skia, не DirectX/OpenGL** — для барів і тексту GPU
  є чистим overhead'ом; копія framebuffer'а тривіально дешева (0.012%
  одного ядра в спокої для 0.7.0, див. Споживання ресурсів).
- **Blur через `SetWindowCompositionAttribute` ACCENT_ENABLE_BLURBEHIND (3)** —
  у acrylic (4) відомий баг DWM (кидає блюр при перетягуванні/зміні
  монітора). Accent перезастосовується циклом off→on після drag, при
  фокусі та при зміні DPI — це змушує DWM перезапустити завислий блюр.
- **Drag стартує з першого CursorMoved далі ніж на 4 px**, а не з кліку:
  кешована позиція курсора може бути застарілою одразу після контекстного
  меню, через що вікно колись телепортувалось, а клік, під час якого курсор
  трохи зрушив, лишається кліком.
- **2 tokio-воркери** — дефолтний воркер-на-ядро (тут 32) марнував ~30
  потоків на кілька крихітних HTTP-запитів за цикл.
- **Один екземпляр** через named mutex у `main.rs`. Другий запуск знаходить
  приховане вікно підказки першого за класом і надсилає йому повідомлення:
  віджет, що працює, показується й піднімається без активації, а вітання чи
  повідомлення після оновлення, що чекало, відкривається.
- **Один запит використання на провайдера за цикл.** Допоміжні запити (план
  Cursor щогодини, через десять хвилин після запиту, що нічого не приніс,
  Grok Bot лише поки вибрано його рядок, оновлення сеансу біля закінчення
  строку й ніколи після нього, проєкт Antigravity, доки відповідь його не
  назве, запасний
  per-model endpoint лише після непридатного зведення, відхилений
  usage-токен на паузі 30 хвилин, gh щонайбільше раз на 15 хвилин і ще раз
  одразу після відмови в збереженому токені) перелічено в PROVIDERS.md,
  «Запити за цикл».
- **Проксі Windows без реєстру в CLI.** Функція `system-proxy` у reqwest
  додала б до `ailimits-auth.exe` імпорти реєстру й крейт, тож
  `providers/proxy.rs` читає три значення Internet Settings викликами, які
  exe віджета вже робить, і лише після того, як `app::run` викликає
  `follow_windows_proxy()`; код, якого CLI не викликає, у нього не
  лінкується. `HTTPS_PROXY`, `HTTP_PROXY` і `ALL_PROXY` і далі мають
  пріоритет; PAC не підтримується.
- **Свідомо без нових DLL.** Довіра корпоративним кореневим сертифікатам
  (rustls-native-certs, платформний верифікатор чи native-tls) додала б
  crypt32 чи schannel; провайдер UI Automation для екранних дикторів додав
  би `uiautomationcore.dll` і субкласинг вікна. Обидва лишено поза exe, щоб
  таблиця імпорту лишалася такою, як є (найменший ризик для антивірусів);
  такі мережі пишуть "untrusted certificate, retrying", а заголовок вікна
  вибору називає його режим для Екранного диктора.
- **tao зафіксовано на 0.37.0, з одним доданим виправленням.** `Cargo.toml`
  фіксує `tao = "=0.37.0"`: починаючи з 0.37.1, `set_visible(true)` для
  вікна, створеного з `with_focused(false)`, забирає фокус (`open_quietly`
  вікна вибору забирало б клавіатуру), а 0.37.3 додає імпорт
  `imm32!ImmSetCandidateWindow`. `[patch.crates-io]` збирає його з
  `vendor/tao`: 0.37.0 у тому вигляді, як його опубліковано, плюс
  виправлення tao#1394 (подія, надіслана через `EventLoopProxy`, могла
  заморозити event loop). Див. `vendor/README.md`.
- **SQLite через власний `winsqlite3.dll` Windows, а не вбудований рушій** —
  Cursor тримає модель, вибрану для Agent, у SQLite-базі, і один
  індексований SELECT на хвилину не виправдовує вкомпільованого SQLite:
  `rusqlite` з `bundled` додає до exe `release-min` близько 1 МБ (+29%),
  FFI-читач разом із першим кодом Cursor — 13 КБ (виміряно 2026-11-10). DLL
  постачається з Windows 10 і 11 і вантажиться лише з System32
  (`LOAD_LIBRARY_SEARCH_SYSTEM32`) при першому запиті, після чого лишається.
  Це не імпорт, тож машина без неї отримує чесну помилку, а не exe, що не
  стартує. У теці чужого застосунку ніколи нічого не пишеться й не
  створюється: WAL-базу, власник якої закритий (немає `-wal`), відкривають
  як `file:...?immutable=1` (на шляху без такої форми, UNC, її не
  відкривають зовсім, `SqliteError::NotQuietly`); ту, власник якої працює,
  і базу з rollback-журналом — `SQLITE_OPEN_READONLY`, з busy timeout
  200 мс.
  Виміряно: ~0.6 мс на запит; +0.2 МБ приватної пам'яті після першого, з
  виходом на плато нижче +0.5 МБ за 21 000 запитів.
- **Чесні стани відображення** (див. PROVIDERS.md): retention → сірий +
  давність → оцінки `≈0%` після гарантованого скидання. Один предикат,
  `ProviderData::is_aged` (застаріле чи оцінка), керує і сірими рядками
  віджета, і блідішим чорнилом панелі на таскбарі; кеш перемальовування
  панелі тримає його для кожного намальованого рядка, тож рядок
  перемальовується, коли стає застарілим чи знову свіжим, і більше жодного
  зайвого разу.
- **Монотонний якір застарілості**: чи live-дані «застарілі» — вирішується за
  монотонним годинником (`ProviderData.received_at: Instant`), а не настінним,
  тож стрибок часу (NTP/VM/DST) не може хибно посіріти свіжі дані чи вигадати
  скидання. Настінний час лишається для показу давності й відліків; оцінка
  `≈0%` ще й вимагає, щоб скидання минуло понад невелике вікно grace.
- **Пауза простою не старить дані**: планувальник повідомляє, коли ставить
  опитування на паузу через неактивного чи заблокованого користувача і коли
  відновлює його (`providers::set_polling_paused` → `PollingPause`). Live-дані
  ніколи не застарілі під час паузи, а після неї остання пауза віднімається
  з їхнього монотонного віку. Пам'ятається лише вона одна: між двома паузами
  завжди проходить цикл опитування, тож live-дані, старші за попередню паузу,
  належать провайдерові, що впав, і раніше посіріти для них чесно. Записи
  дискового кешу (без монотонного якоря) лишаються на правилі настінного
  часу.
- **Backoff і одна рання повторна спроба після пробудження.** Цикл, у якому
  впали всі провайдери, подвоює очікування (120, 240, далі 300 с при
  інтервалі 60 с). Після сну машини (настінний годинник пройшов інтервал на
  90 с чи більше) або паузи простою перший цикл, що не отримав жодної
  відповіді, повторюється один раз через 20 с, поки повертається мережа.
- **Згода — одна таблиця конфігу, яку читають у двох місцях.**
  `Config::provider_active` (увімкнений І дозволений через `[reads] sign_in`
  чи `app_sign_in`) вирішує, чи провайдер узагалі працює й показується;
  провайдер, якому нічого не дозволено, будується вимкненим і повертає
  `NotConfigured`, перш ніж торкнутися файлу, keyring, `gh` чи мережі.
  `provider_set` ще й ставить `ProviderConfig::tool_files` лише за
  `sign_in` (ніколи не зберігається), і кожен провайдер перевіряє його перед
  будь-яким джерелом, що належить іншому інструментові: його файлом токена,
  його записом у Credential Manager, `gh auth token`. У межах дозволеного
  `ProviderConfig::auth_method` (`AuthMethod::{Subscription, ApiKey,
  UsageToken}`, джерело, вибране в Sign-in провайдера) визначає те одне
  джерело, яким провайдер користується: вставлений ключ чи usage-токен
  ніколи не підстраховується входом інструмента, а вхід інструмента —
  збереженим токеном. Провайдер, налаштований лише власним входом програми
  (вставлений ключ чи токен використання, власний вхід у Cursor), ніколи не
  читає входу інструмента; його файл налаштувань однаково читається для
  підпису моделі за `[reads] tool_settings`, а найновіша сесія — за
  `last_session`, як і для кожного провайдера, що працює. Якщо у вікні
  вибору зняти всі рядки провайдера,
  викликається `Config::revoke`. Текст кожного запитання береться з
  `consent::READ_INFO`; тести звіряють його сервери з URL у кожному файлі
  під `src/providers` (в обидва боки: кожен хост, який викликається,
  названо, і кожен названий хост викликається), а кожну назву файлу й ціль
  Credential Manager, які читає провайдер, — із текстом.
- **Один розв'язувач шляхів інших інструментів** (`config/paths.rs`,
  `ToolPaths`). Його питають провайдери, підписи моделей, тексти згоди,
  «found on this PC» у вітанні та CLI, тож вони не можуть розійтися.
  `CODEX_HOME`, `GROK_HOME` і `COPILOT_HOME` враховуються лише абсолютними;
  відносне значення робить цей інструмент невідомим (нічого не читається й
  не знаходиться), ніколи не робоча тека і ніколи не тека за
  замовчуванням. `tool_signs` відрізняє власну теку інструмента (сильна
  ознака: галочка у вітанні) від суміжної (слабка: GitHub CLI для Copilot,
  `.gemini` для Antigravity).
- **Звідки взявся конфіг, вирішує, що дозволено** (`storage::Origin`; стан
  встановлює `settle_reads` після проходів `migrate`, що перейменовують і
  дописують відсутніх провайдерів). `FreshInstall` (файлу немає, його не
  вдалося зрозуміти й він відкладений як `config.toml.<штамп>.corrupt`, він
  порожній чи без провайдерів) очищує `[reads]`, вимикає всіх провайдерів,
  тож і старіша версія після відкату нічого не читає, і позначає, що треба
  показати вітання. `Upgrade` (`[[providers]]` без `[reads]`: 0.7.0 і
  старіші) дозволяє кожного провайдера, увімкненого у файлі, і позначає, що
  треба показати одноразове повідомлення. Прохід дописування за будь-якого
  походження додає відсутнього провайдера вимкненим: версія, що записала
  файл, його не знала, тож і не читала. `Current` лишається таким, яким його
  лишив користувач. Файл, який не вдається прочитати (після близько 2 с
  повторів), ніколи не перейменовується: програма працює на конфігу в
  пам'яті, що нічого не читає, а шлях утримується, тож цього сеансу його не
  пише ні записувач, ні фінальне збереження при виході
  (`storage::saving_held`). `storage::peek` читає конфіг, нічого не
  створюючи, не перейменовуючи й не пишучи, — для `ailimits-auth`, і
  називає пропущені рядки (`Peek::LeftOut`): її команди, що змінюють конфіг,
  відмовляються від такого файлу, бо збереження позбавило б його цих рядків.
- **Мало записів власних файлів.** `provider-cache.json` має один
  серіалізований записувач (перемагає найновіший вміст, відповіді одного
  циклу зливаються в один запис); він пишеться, коли змінюються значення,
  ліміти чи час скидання (з точністю до хвилини), інакше не частіше ніж раз
  на 10 хвилин, і при виході. Книга сповіщень (`alerts.json`) пишеться лише
  коли змінилася.
- **Аварія лишає слід, а не дані.** У release-min `panic = "abort"`, тож
  `main.rs` ставить panic hook, який дописує один рядок у `crash.log`
  (UTC-час, версія, потік, `file:line:col`, шляхи залежностей скорочено до
  `crate-x.y.z\src\...`) і ніколи — текст паніки, який може цитувати текст,
  що його різали. Невдалий старт пише туди `could not start: <помилка>` і
  показує «AI Limits could not start.» зі шляхом до файлу. Понад 64 КБ
  файл стає `crash.log.1` (замінюючи попередній) і починається заново.
- **Вигляд за замовчуванням зафіксовано.** Поки `[ui.rows]` і `[ui.model]` не
  задані, `rows::visible_rows` дає по одному рядку на провайдера з його
  даними без змін. Підказка панелі — єдине змінене значення за
  замовчуванням: коли `[ui.tooltip]` не задано (Percent і Reset time обидва
  ввімкнені), вона дає кожному провайдеру рядок із його скиданням; лише
  Percent дає колишній один рядок 0.7.0. Див. «Візуальний еталон» нижче.
- **Назви моделей обмежено справжньою шириною, а не кількістю символів.**
  `rows::NAME_SLOTS` перелічує найвужчі місця, де renderer малює назву
  моделі (ширина й розмір шрифту); `name_fits` міряє через
  `Renderer::text_width`, тією самою мірою, що й `draw_text`, тож
  перейменована модель видна повністю в кожному розмірі. Тест renderer'а
  звіряє цей перелік із геометрією. Назви зберігаються за
  `choices::model_key`: id моделі або `"provider:id"` для власного роутера
  інструмента (`auto`, `default`), і віджет шукає їх через
  `choices::model_name`, як і вікно вибору.
- **Вікно вибору — чистий автомат станів за тонким вікном.** `Picker` бере
  `PickerEvent` і повертає `PickerAction` плюс `PickerScene` із фігур, і все
  це тестується без вікна; `PickerWindow` показує його через softbuffer, як
  віджет, перемальовує лише на ввід і не має таймерів. Буфер обміну він
  читає лише на Ctrl+V чи Shift+Insert у поле назви, яке редагується
  (вставлення в Sign-in читає застосунок, `app/clipboard.rs`). Воно йде за
  світлим чи
  темним режимом застосунків (`AppsUseLightTheme`), високою контрастністю
  (системні кольори) і розміром тексту Windows; його запитання
  прокручується, а кнопки завжди видно; опис рядка показується при
  наведенні й при фокусі з клавіатури; поки набирається назва, панель
  оболонки (Win+V, Win+.), що забирає фокус, його не закриває.

## Оновлення і релізи

- **Канал визначається лише з локальних фактів, до будь-якої мережі.**
  `updater::channel()` читає ідентичність пакета
  (`GetCurrentPackageFullName`) і власний запис деінсталяції інсталятора:
  `Store` і `Unmanaged` (Scoop, портативний zip, власна збірка) одразу
  повертаються, тож ніколи не звертаються до api.github.com, а в їхньому
  меню немає пункту *Automatic updates* (`self_update_supported`). Далі йде
  лише копія `Installer`.
- **Перевірити, зачекати, звірити.** Приблизно через 30 с після старту,
  далі щодоби, оновлювач питає в GitHub Releases API останній реліз (через
  проксі Windows, як і провайдери). Увімкнення *Automatic updates*
  запускає перевірку приблизно за 10 с (`AutoUpdate`, `SWITCHED_ON_DELAY`;
  якщо тим часом галочку зняли, нічого не питається), якщо за останню
  годину перевірки не було. Оновлювач бере лише асет `AiLimits-Setup-<v>.exe` з його `.sig`.
  Новіший реліз чекає, поки користувача не буде 5 хвилин (без вводу або із
  заблокованим сеансом, `platform::user_idle_secs`), перевіряючи щохвилини
  (вимкнення *Automatic updates* тим часом це оновлення скасовує; поки
  воно чекає, щоденної перевірки немає, тож реліз, що вийшов тим часом,
  прийде з наступною перевіркою після цього встановлення); далі
  інсталятор завантажується й звіряється двічі: із SHA-256, який GitHub
  публікує для асета, і з підписом Ed25519 ключем, вбудованим у програму
  (`RELEASE_KEYS`, key id `1507bd92b1a4bb7b`). Підпис покриває ім'я файлу і
  його SHA-256, тож підписаний інсталятор не видати за іншу версію. Немає
  підпису або він не сходиться — встановлення немає. Якщо користувач
  повернувся під час завантаження, оновлення знову чекає. Кожен запит,
  зокрема завантаження, має тайм-аут 120 с, а кожна відповідь читається до
  межі (реліз 1 MiB, підпис 1 KiB, інсталятор 64 MiB; він близько 4 MB).
  URL API незмінний, а URL завантажень — це `browser_download_url` із
  відповіді як є; редирект після будь-якого з них виконується лише на https
  зі стандартним портом до github.com, api.github.com чи хоста асетів
  `*.githubusercontent.com`, не більше п'яти.
- **Файл підпису.** `.sig` — це один рядок,
  `ailimits-signature-v1 <id ключа> <підпис>`: id ключа — 16 hex-цифр,
  перші 8 байтів SHA-256 відкритого ключа, далі підпис Ed25519 — 128.
  Підписується саме той текст, який будує `signature::signed_message`,
  `"AI Limits release signature v1\nfile <ім'я>\nsha256 <hex>\n"`, де
  `<ім'я>` — опубліковане ім'я файлу, `<hex>` — SHA-256 його байтів малими
  hex-цифрами, а `\n` — переведення рядка. Сьогодні вбудований ключ
  (`RELEASE_KEYS`) —
  `8691886023426a4f882779d754feaf850e977d5e70710013c092e4aca02c0dd9`, id
  `1507bd92b1a4bb7b`. Завантажений файл може перевірити будь-хто, ключ для
  цього не потрібен:
  `cargo run --locked --release --manifest-path tools/release-signer/Cargo.toml -- verify <файл>`,
  з його `.sig` поруч і під опублікованим ім'ям.
- **Відмова в оновленні тиха.** Реліз без `AiLimits-Setup-<v>.exe`, без
  його дайджесту SHA-256 чи без його `.sig` відхиляється ще до будь-якого
  завантаження; підпис, який не читається, — до завантаження інсталятора;
  інсталятор, чий дайджест чи підпис не сходиться, — після нього. Кожна
  відмова — це один рядок у лозі рівня debug
  (`auto-update check skipped: ...`): користувачеві нічого не
  повідомляється, `update-attempt.json` не пишеться, тож та сама перевірка
  повторюється при наступній щоденній перевірці й на кожному старті. Після
  заміни ключа копію, яка довіряє лише старому ключу й пропустила
  перехідний реліз (він підписаний старим ключем і довіряє обом),
  відхиляють щоразу, і її доводиться оновити вручну.
- **Підписи захищають оновлення, починаючи з 0.7.1.** Копія 0.6.0-0.7.0
  оновлюється власним оновлювачем (`git show v0.7.0:src/updater.rs`): він
  бере перший асет релізу, ім'я якого закінчується на `.exe`, перевіряє
  лише дайджест SHA-256, який GitHub повідомляє для нього, і ніколи `.sig`,
  і встановлює одразу, не чекаючи, поки користувача не буде, через
  `%TEMP%\ailimits-update.cmd`. Тож оновлення до 0.7.1 тримається лише на
  цьому дайджесті, і поки такі копії існують, реліз мусить мати рівно один
  `.exe` — інсталятор. `release.yml` додає рівно один: інші exe лежать у
  zip.
- **Запускається саме перевірений файл.** Перевірений інсталятор
  записується в теку, створену заново для цього завантаження,
  `%TEMP%\AiLimits-update-<випадкове>` (`create_new`), і утримується від
  останньої перевірки до запуску: відкритий лише зі спільним читанням, тож
  ніхто не може його записати, перейменувати чи видалити, перечитаний через
  цей дескриптор проти перевіреного SHA-256 і відкритий, доки процес
  інсталятора не стартував. Його тека видаляється разом із ним.
- **Без скрипту посередині.** Спершу спроба записується в
  `update-attempt.json` (версія, шлях до інсталятора, `told`), далі сам
  інсталятор запускається через `CreateProcessW` (шлях як UTF-16, тож шлях
  профілю чи TEMP із кирилицею, `&` чи `%` працює як будь-який інший) лише з
  ASCII-ключами: `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART
  /CLOSEAPPLICATIONS /RELAUNCH=1`. Програма завершується; запис `[Run]`
  інсталятора з `Check: RelaunchAfterUpdate` запускає нову версію з теки
  встановлення лише в тихому запуску з `/RELAUNCH=1`, тож тихе встановлення
  winget і Chocolatey, як і раніше, нічого не запускає. 0.6.0-0.7.0
  передавали роботу `.cmd`-скрипту в `%TEMP%`, який падав на таких шляхах;
  0.7.1 прибирає те, що від нього лишилося (`ailimits-update.cmd`,
  `AiLimits-Setup-<поточна>.exe`).
- **Невдале оновлення само не повторюється.** Якщо після спроби програма й
  далі старішої версії, ця версія сама більше не пробується (новіший реліз
  — так), завантажений інсталятор видаляється, а наступний старт показує
  одне повідомлення (`updater::unfinished_update_note`, позначка `told`).
- **Релізний конвеєр** (`.github/workflows/release.yml`, на тег `v*`):
  кожна дія прив'язана до SHA коміту, checkout без збереженого токена, без
  кешу збирання, Inno Setup 6.7.4 зафіксовано за SHA-256, і три завдання,
  кожне на чистій машині. *build* (без секрету, токен лише для читання)
  запускає fmt, clippy і тести, перевіряє, що тег, `Cargo.toml` і
  `installer/ailimits.iss` збігаються, збирає exe, переписуючи шляхи
  машини збирання на `~` (`USERPROFILE`) і `ailimits`
  (`GITHUB_WORKSPACE`) через `--remap-path-prefix`, доданий через
  `--config`, щоб лишився `+crt-static` з `.cargo/config.toml` (змінні
  `RUSTFLAGS` замінили б його); наступний крок зриває реліз, якщо exe досі
  називає `VCRUNTIME140`, `api-ms-win-crt-` чи шлях збирання. Далі він
  збирає інсталятор і портативний zip. Локальна збірка чи збірка в ci.yml
  шляхів не переписує. *sign* (середовище `release`, єдине завдання з
  ключем) одразу падає без секрету, збирає
  `tools/release-signer` з чистого checkout, ще до того як ключ стає
  доступним, підписує файли, які передало *build* (дайджести артефактів
  перевіряються), і звіряє кожен підпис із `RELEASE_KEYS`, тож хибний
  секрет зриває реліз, а не оновлення користувачів. Жодна інша залежність
  застосунку ніколи не виконується там, де є ключ. *publish* (єдиний токен
  на запис) перевіряє, що кожен файл має підпис, і створює реліз
  **чернеткою**, з розділом CHANGELOG цієї версії як нотатками. Супровідник
  перевіряє файли (VirusTotal, швидке встановлення) і публікує його вручну:
  `gh release edit vX.Y.Z --draft=false`. Тег без розділу `## <версія>` у
  CHANGELOG.md отримує натомість нотатки, згенеровані GitHub.
- **Запуск вручну** (`workflow_dispatch`) виконує лише *build*, без
  перевірки версії тегу: нічого не підписується й не публікується. Його
  файли — артефакт `release-files` цього запуску, що зберігається 7 днів,
  щоб перевірити їх до тегу.
- **Версія Rust.** Файлу `rust-toolchain` немає: CI і реліз збирають
  поточним stable Rust того дня, а від нього залежать таблиці імпорту exe.
  Мінімум, 1.90 (`rust-version` у Cargo.toml), тримає `cargo check` у
  ci.yml.
- **Ключ підпису.** Закритий ключ супровідник тримає офлайн і в секреті
  `AILIMITS_RELEASE_SIGNING_KEY` середовища `release`. Додати його (один
  раз) — передаючи ключ через stdin, щоб він ніколи не з'явився в
  командному рядку:

  ```
  gh api -X PUT repos/napxlexn/ailimits/environments/release
  Get-Content -Raw <release-signing-key.hex> |
      gh secret set AILIMITS_RELEASE_SIGNING_KEY --env release --repo napxlexn/ailimits
  ```

  Зробіть резервну копію офлайн (зашифрований диск чи менеджер паролів):
  без нього не підписати жодного релізу для 0.7.1 і новіших, і кожному
  користувачеві довелося б один раз оновитися вручну. Новий ключ:
  `release-signer keygen` у нову теку, його відкритий ключ — у
  `RELEASE_KEYS` поруч зі старим, реліз, підписаний СТАРИМ ключем, заміна
  секрету, а через реліз — прибрати старий ключ із `RELEASE_KEYS`.
  Подробиці — у `tools/release-signer/src/main.rs`.

## Візуальний еталон

`ui/visual_baseline.rs` (лише тести) малює віджет, панель, трей-іконку й
підказку при наведенні з конфігом за замовчуванням і сталими даними та
звіряє хеш кожного pixmap із `tests/visual/<група>.txt`.

- **Закріплені групи** (`widget`, `panel`, `tray`) записано в 3e8aa80
  (2026-11-11), а не намальовано з тегу 0.7.0. Вони тримають вигляд того
  коміту, який навмисно відрізняється від 0.7.0, і власник це схвалив:
  застарілі дані сіріють ще до скидання (ac17bd2); панель малює застарілий
  чи оціночний рядок блідішим чорнилом (a755fe3); дані застарілі, щойно
  минув інтервал оновлення плюс хвилина (9eada81); гарантовано минуле
  скидання одразу читається як приблизно 0 (387fc59); підказка над
  застарілим рядком, помилка якого минає сама, показує лише її, де 0.7.0
  додавала дію провайдера («offline, retrying — check gh auth»), пораду, що
  не допомагала (3d6093c). Намальовані проти тегу 0.7.0 з тими самими
  фікстурами, урізаними до того, що вміє 0.7.0, 83 зі 116 записів віджета,
  30 із 36 панелі і всі 84 трею збіглися до байта; решта відрізняється лише
  через ac17bd2, a755fe3 і 3d6093c (9eada81 і 387fc59 змінюють правила, а
  не малювання). Вони змінюються лише за рішенням власника
  (`UPDATE_PINNED_BASELINE=1`); ніколи не перезаписуйте їх, щоб пройшов
  тест.
- **Інші групи** (`picker`, `widget-rows`, `tooltip-rows`,
  `panel-numbers`: відсоток панелі, час скидання чи обидва, зі смужкою чи
  без неї, або сама смужка, кожен у розмірі, який дає програма;
  `widget-numbers`: кожне поєднання `[ui.widget]`, крім типового, у кожній
  розкладці, з моделями; `tray-styles`: інші види іконки трею;
  `widget-tune`,
  `panel-tune`, `tray-tune`: ручки `[tune]`, відмінні від значень за
  замовчуванням, кожна окремо і кілька разом) покривають новий вигляд; їх
  перезаписують через `UPDATE_BASELINE=1` лише за навмисної зміни, про яку
  сказано в коміті. Самі значення `[tune]` за замовчуванням тримають
  закріплені групи, які малюються без таблиці `[tune]`.
- **Шрифт.** Кожен хеш залежить від шрифту інтерфейсу (першого з
  `renderer::FONT_CANDIDATES`, що вантажиться). `tests/visual/font.txt`
  записує його (`segoeui.ttf`, Segoe UI 5.72, і його SHA-256). На машині, що
  малює іншим шрифтом, кожна група пропускається з видимим попередженням
  «font differs, baseline not comparable» замість падіння, і нічого там не
  можна записати.
- При розбіжності PNG змінених записів лягають у
  `%TEMP%\ailimits-visual\<група>\`; `DUMP_VISUAL=1` пише всі записи.

## Споживання ресурсів (виміряно, не оцінено)

Еталонний стовпець таблиці — вимір 0.7.0 від 2026-09-23: 254 с на тихій
машині (грало відео і більше нічого; без підвищених прав, тому рядки про
роздільність таймера й SRUM перенесені з серпневого прогону;
`bench/results/perf-audit-2026-09-23_0424.json`). Панель уже питала шелл

видима; близько 20 МБ пам'яті — це UI Automation, завантажена для цього

README наводить перший прогін 0.7.1, коміту b1ca5da від 2026-11-21 (322 с,
`bench/results/perf-audit-2026-11-21_0423.json`): 0.0097% одного ядра

вимірюють так само перед її релізом.
