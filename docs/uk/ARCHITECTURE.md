# ARCHITECTURE.md — як влаштований віджет

Однопотоковий **event loop tao** плюс маленький **tokio runtime**
(2 воркери) для мережевих запитів. UI рендериться на CPU
(tiny-skia → softbuffer), тож GPU не потрібен узагалі.

```
main.rs ── захист від другого екземпляра, логування, app::run()
   │
app.rs ─── володіє всім: конфіг, дані, вікно, меню
   ├── monitor/scheduler.rs   tokio-задача: цикл fetch_all → sleep(interval)
   │     └── providers/       claude.rs / codex.rs / copilot.rs / antigravity.rs
   ├── ui/renderer.rs         малювання tiny-skia (ЄДИНЕ місце, що малює)
   ├── ui/layout.rs           прямокутники зон за лейаутом/деталізацією
   ├── ui/theme.rs            всі кольори (ЄДИНЕ джерело кольорів)
   ├── ui/context_menu.rs     нативне меню muda
   ├── ui/tray.rs             трей-іконка, спільне малювання гліфів і tooltip
   ├── ui/taskbar_panel.rs    індикатор-overlay на таскбарі (layered-вікно)
   ├── monitor/trend.rs       burn-rate проєкція (опційний прогноз)
   ├── platform/win.rs        Win32: WinEvent-стеження за таскбаром/треєм,
   │                          layered-презентація, промоція трей-іконок
   ├── updater.rs             щоденне опитування GitHub Releases, перевірка
   │                          SHA-256, тихе встановлення + перезапуск
   ├── platform/taskbar_geom.rs  чисті правила розміщення/фолбеку панелі
   │                          (тестуються без Win32)
   ├── config/ (schema.rs, storage.rs)  структури конфігу + толерантний TOML
   └── notifications/toast.rs Windows-тости
```

## Потік даних

```
[Scheduler] --sleep(SharedInterval)--> [Provider::fetch()]
        кожен провайдер у власній tokio-задачі
                  │ ProviderData
        tokio mpsc → EventLoopProxy(UserEvent::Command)
                  │
   [event loop: обробник UpdateProvider]
   ├─ перевірка порогу для toast (з cooldown)
   ├─ merge/збереження provider-cache (непротухлі метрики переживають рестарт)
   ├─ retention застарілих даних (помилки не затирають реальні дані)
   └─ visible_data() → resize при появі/зникненні рядка → redraw
```

Кліки меню йдуть тим самим шляхом: `muda::MenuEvent` → proxy →
`UserEvent::Menu` → обробники змінюють конфіг, перебудовують провайдерів
(`SharedProviders` — це `Arc<RwLock<Vec<Arc<dyn Provider>>>>`, спільний зі
scheduler'ом), зберігають конфіг і просять redraw.

## Ключові рішення

- **softbuffer + tiny-skia, не DirectX/OpenGL** — для барів і тексту GPU
  є чистим overhead'ом; копія framebuffer'а тривіально дешева, CPU у
  спокої 0%.
- **Blur через `SetWindowCompositionAttribute` ACCENT_ENABLE_BLURBEHIND (3)** —
  у acrylic (4) відомий баг DWM (кидає блюр при перетягуванні/зміні
  монітора). Accent перезастосовується циклом off→on після drag, при
  фокусі та при зміні DPI — це змушує DWM перезапустити завислий блюр.
- **Drag стартує з першого CursorMoved**, а не з кліку: кешована позиція
  курсора може бути застарілою одразу після контекстного меню, через що
  вікно колись телепортувалось.
- **2 tokio-воркери** — дефолтний воркер-на-ядро (тут 32) марнував ~30
  потоків на три крихітні HTTP-запити за цикл.
- **Один екземпляр** через named mutex у `main.rs`.
- **Чесні стани відображення** (див. PROVIDERS.md): retention → сірий +
  давність → оцінки `≈0%` після гарантованого скидання.
- **Монотонний якір застарілості**: чи live-дані «застарілі» — вирішується за
  монотонним годинником (`ProviderData.received_at: Instant`), а не настінним,
  тож стрибок часу (NTP/VM/DST) не може хибно посіріти свіжі дані чи вигадати
  скидання. Настінний час лишається для показу давності й відліків; оцінка
  `≈0%` ще й вимагає, щоб скидання минуло понад невелике вікно grace.

## Споживання ресурсів (виміряно, не оцінено)

Аудит 2026-08-23 скриптом `bench/perf_audit.ps1` (5 хв на 1 Гц, запущений
`release-min`, Win11 26200, Ryzen 9 9950X3D / 32 потоки, elevated). CPU —
точний облік ядра ОС, не семплінг. Звіт:
`bench/results/perf-audit-2026-08-23_0740.json`. Прогін 2026-07-08 лежить
поруч як `perf-audit-published-2026-07-08.json` і показував 0.024% ядра та
61 МБ — те саме вікно на тій самій машині, на п'ять релізів раніше.

| Метрика | Виміряно |
|---|---|
| CPU (точний облік) | 0.016 CPU-с за 327 с = **0.005% одного ядра** (0.0002% машини) |
| GPU | **0%** — у процесу взагалі немає інстансів лічильників GPU-движків (CPU-рендеринг) |
| Working set | 37 МБ середнє / 40 МБ пік |
| Потоки | ~10 середнє / 13 пік |
| Хендли | ~377 |
| I/O | 184 Б/с середнє; піки — HTTPS циклу оновлення (3 запити/цикл, < 5 КБ кожен) |
| Context switches (проксі idle-пробуджень) | ~8.5/с у середньому за вікно |
| Роздільність системного таймера | **не піднімається** (`powercfg /energy`: жодного запиту від ailimits) |
| Оцінка енергії SRUM | ~160 одиниць/хв — лише CPU + мережа; дисплей/диск/GPU нульові (з звіту 2026-07-08; серпневий прогін зберігає сирі погодинні відра, не цю нормалізацію) |
| Вплив на DPC/latency | неможливий: user-mode, без драйверів, без запитів роздільності таймера |
| Бінарник (`release-min`) | ~3 МБ |
